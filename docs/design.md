# 详细设计文档

## 1. 问题描述

在真实安全运营场景中，企业资产对外暴露面是一个持续变化的风险面。核心痛点：

1. **资产清单与实际暴露不一致**：资产登记时认为某个端口是内部服务，但网络变更后变成了对外暴露
2. **管理端口误暴露**：开发/运维临时开放管理端口（Docker API、K8s API、Redis 等）后忘记关闭
3. **调试接口遗留**：Spring Boot Actuator、Jolokia 等调试接口在上线后未关闭
4. **传统扫描工具缺乏判据沉淀**：Nmap 等工具能发现开放端口，但判据无法版本化、审计、迭代

## 2. Agent 增量价值

与直接用 Nmap/Nessus 相比，Agent 的增量价值在于：

| 维度 | 传统工具 | 本 Agent |
|------|----------|----------|
| 判据管理 | 脚本内置，不可追溯 | YAML 规则文件，可版本化审计 |
| 误报控制 | 依赖人工经验 | 误报特征库自动降级（CDN/蜜罐/代理） |
| 优先级排序 | 简单严重度分级 | 多维矩阵（资产关键性 × 规则置信度 × 事件频率） |
| 留痕 | 日志文件 | NDJSON 结构化审计日志 |
| 能力调用 | 直接执行 | 经 OctoBus 网关，统一鉴权审计 |
| 知识迭代 | 经验在个人脑中 | 规则文件可逐步积累和复用 |

## 3. 五段闭环设计

### 3.1 触发 (Trigger)

- **方式**：cron 定时触发，每日 02:00 执行
- **选择理由**：暴露面巡检是周期性全量扫描活动。事件驱动（如新资产注册触发）会导致重复扫描且无法检测累积模式（端口组合风险）。cron 确保一致的全量基线覆盖。
- **配置**：`agent-compose.yml` 中 `trigger.type: cron, schedule: "0 2 * * *"`

### 3.2 取数 (Data Collection)

- **方式**：经 OctoBus 网关调用 portscan 和 assetquery 服务
- **内容**：
  1. 调用 `assetquery.default.query_assets` 获取资产清单
  2. 对每个资产调用 `portscan.default.scan_ports` 执行端口扫描
  3. 收集开放端口的 Banner 和响应头
- **为何不用 LLM**：端口扫描是确定性网络操作，不需要模糊判断。LLM 无法可靠解析二进制 Banner 数据，网络错误需要确定性重试逻辑。

### 3.3 判定 (Analysis)

判定模块是 Agent 的核心，分两层：

**第一层：规则引擎（确定性代码）**
- 加载 `knowledge/*.yaml` 规则文件
- 对每个开放端口执行三重判定：
  1. 黑名单匹配（端口本身就不应对外）
  2. 条件暴露判定（需 Banner 分析确定风险）
  3. 端口组合检测（跨端口攻击链）
- Banner 分析使用特征串精确匹配，包括高危特征和误报特征

**第二层：LLM 模糊判断（仅对 ambiguous findings）**
- 仅在 Banner 为空且端口为条件暴露类型时调用
- LLM 不做最终分类，只提供上下文分析
- LLM 分析结果作为报告附录，不进入风险评分

### 3.4 产出 (Report)

- JSON 报告：机器可读，可集成到工单系统/SOC 平台
- Markdown 报告：人类可读，按优先级排列，含证据链
- 报告包含：执行摘要、按优先级分组的发现列表、每条发现的规则 ID/证据/建议

### 3.5 留痕 (Audit)

- NDJSON 格式审计日志（每行一个 JSON 对象）
- 记录：cycle_start → trigger → data_collection → octobus_call → analysis → llm_call → report_generated → cycle_end
- 与 OctoBus 服务端审计日志可交叉验证

## 5. 不经网关直接调用后端接口的问题

如果 Agent 不经 OctoBus 而直接调用后端服务，存在以下 5 个层面问题：

1. **凭据/密钥失控**：密钥散落在 Agent 环境变量中，无法统一管理轮换。资产数据库凭据暴露给 Agent 容器。
2. **鉴权与最小权限缺失**：绕过 capset 的方法级白名单，Agent 可调用未授权方法。例如 capset 只授予 `scan_ports`，但直接调用可访问 `stop_service` 等危险方法。
3. **审计缺失**：无统一访问日志。OctoBus 的 NDJSON 审计日志记录每次调用的协议/capset/方法/状态码/耗时，出事可溯源。直连无此记录。
4. **暴露面扩大**：后端服务端口被迫对 Agent 网络开放。portscan 和 assetquery 服务需要绑定到可达地址，扩大了攻击面。
5. **治理失效**：无法做协议统一（gRPC/Connect/MCP）、限流、能力编排与版本控制。每个 Agent 自己实现调用逻辑，无法统一管控。

## 6. 部署关键选择

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 运行时驱动 | docker | 容器隔离，沙箱安全，易于管理 |
| 触发方式 | cron | 周期性全量扫描，非事件驱动 |
| 协议 | Connect RPC | HTTP/1.1 友好，JSON 映射，调试方便 |
| OctoBus 绑定 | 127.0.0.1 only | 不对公网发布端口 |
| 控制面鉴权 | AUTH_SECRET + HTTPS | 防止任意人 up/down 智能体 |
| 自动恢复 | restart:always + healthcheck + depends_on | 确保重启后有序恢复 |
| 模型选择 | gpt-4o-mini | 成本低，模糊判断任务不需要大模型 |
