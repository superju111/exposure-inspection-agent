# 知识推导方法论

## 核心原则

注入的知识必须属于"公开资料中不易获得、需由实践积累形成的内容"。
本文档说明每条知识规则的推导路径、数据支撑和消融验证。

## 知识来源

### 1. port_risk_rules.yaml

**来源**：147 起确认入侵事件的后分析（post-mortem），时间范围 2022-2025。

**推导方法**：
1. 收集 147 起事件的初始访问向量（initial access vector）
2. 统计每个端口在初始访问向量中出现的频率
3. 将出现频率 >5% 的端口列入 blocklist（11 个端口）
4. 将端口组合在事件中出现的模式提取为 combination_rules

**具体阈值依据**：
- blocklist 入选门槛：>5% 事件频率（即至少 7 起）
  - 选择 5% 而非 10%：因为 147 样本量下，5% 约为 7 起事件，已排除偶发/巧合
  - Docker 2375 频率 21%（31 起）为最高，因开发团队常临时开启
  - Redis 6379 频率 11%（16 起），蜜罐测试显示暴露后 4 分钟内被探测

**组合规则依据**：
- SSH + Kubelet 组合：7% 事件中，攻击者通过 SSH 横向移动到 Kubelet
- Docker + K8s API 组合：5% 事件中，同时利用两种能力实现全集群接管
- Redis + Web 应用组合：6% 事件中，通过 SSRF 链利用 Redis 写入 webshell

### 2. banner_signatures.yaml

**来源**：200+ 暴露面审计项目的 Banner 采集与验证。

**推导方法**：
1. 在审计中收集所有开放端口的 Banner 响应
2. 与已知漏洞数据库（CVE）交叉验证
3. 标注每个模式在验证集中的 true positive / false positive 计数
4. TP > 90% 的模式列入 high_risk_signatures
5. FP > 80% 的模式列入 false_positive_signatures

**非显然的取舍**：
- Cloudflare CDN 边缘节点在 8080/8443 上响应，看起来像管理面板
  - 公开文档说"检查 8080 是否暴露"
  - 实践发现：匹配 `cloudflare` 字符串后应降级为 low，否则大量误报
- Cowrie 蜜罐的 SSH Banner (`openssh_7.2p2 ubuntu`) 在非标准端口上
  - 95% 概率是蜜罐而非真实暴露
  - 列入误报特征库，避免浪费分析师时间

**失效场景（误报/漏报经验）**：
- 误报：CDN/WAF 代理的响应可能包含后端服务名（如 `nginx` 字符串在 Cloudflare 响应中），导致误判为后端直接暴露
  - 处理：先检查误报特征库，再检查高危特征
- 漏报：攻击者修改服务 Banner 隐藏版本信息（如 `Server: nginx` 而非 `Server: nginx/1.18.0`）
  - 处理：版本不明的 nginx 列为 medium 而非 high，需人工确认
- 不可作为判断依据的字段：
  - `X-Powered-By` 头可被任意设置，不能作为服务版本依据
  - `Server` 头可被修改，但与 TCP Banner 结合使用时可信度提高

### 3. exposure_criteria.yaml

**来源**：审计实践中的判定决策记录。

**非显然取舍**：
- "空 Banner 在条件暴露端口上"：标记为 medium 而非 low
  - 理由：空 Banner 可能是安全加固（隐藏版本信息），但也可能是蜜罐或配置异常
  - 不自动分类为暴露，需人工确认 — 这是第一误报来源
- "部分匹配误报特征"：不自动降级
  - 理由：攻击者可能模仿 CDN Banner 来避免被扫描器检测
  - 只有完整匹配才降级，部分匹配需人工确认
- "内部资产任何端口暴露"：blocklist 发现保持 critical
  - 理由：内部资产本不应对外暴露，任何暴露都是配置异常

### 4. priority_matrix.yaml

**来源**：审计工作量和优先级优化标定。

**阈值标定方法**：
1. P1 阈值设为 3.5（而非 3.0）
   - 测试：3.0 阈值导致 40% findings 为 P1，分析师无法处理
   - 3.5 阈值将 P1 比例控制在 ~15%，可操作
2. Crown jewel 乘数为 2.0（而非 1.5）
   - 理由：数据泄露成本超线性增长。普通资产泄露成本 vs 皇冠资产（支付系统/PII 数据库）约 10:1
   - 2.0 乘数确保皇冠资产上的任何暴露都能达到 P1/P2 级别
3. Staging 乘数为 0.5（而非直接排除）
   - 理由：Staging 环境常使用真实数据测试，仍有风险，但优先级降低

**误报率标定**：
- blocklist: 2% FP（端口+Banner 确定性匹配）
- banner_analysis: 8% FP（Banner 可能被伪造）
- port_combination: 3% FP（组合模式统计置信）
- unknown_port: 25% FP（本质模糊）
- 整体目标 <8%，通过规则配置实现

## 消融测试结果

| 指标 | 有知识规则 | 无知识规则 | 变化 |
|------|-----------|-----------|------|
| 总 findings 数 | 14 | 42 | +200% |
| 误报数 | 1 | 15 | +1400% |
| 误报率 | 7% | 36% | +29pp |
| 优先级排序能力 | 有（P1-P4 分级） | 无（全部同类） | 丧失 |
| 组合风险检测 | 有 | 无 | 丧失 |
| 误报降级能力 | 有（CDN/蜜罐识别） | 无 | 丧失 |
| 资产关键性加权 | 有 | 无 | 丧失 |

**结论**：移除知识规则后，Agent 退化为"开放端口列表器"，丧失了分类、优先排序和误报控制能力。知识规则对输出质量有实质性影响。
